# Firmware F1.3.8dev2 — soft-switch phase in the PAL-accurate renderer

This development build corrects the timing of three video soft switches in
the two PAL-accurate colour modes. It contains everything in
[F1.3.8dev1](F1.3.8dev1.md), with the same FPGA image.

## Video

The firmware has two video renderers. The colour modes "PAL composite" and
"PAL TV" use the PAL-accurate renderer. All other colour modes use the clean
renderer.

In October 2026 (F1.3.2), VIDSYNC from the VidModes disk showed three
switches at the wrong cycle in ONE//e. The correction went into a table that
acts on the capture records before either renderer sees them. That table
was tuned with the clean renderer. The PAL-accurate renderer has its own
signal model of the TEXT and 80COL latency, so the same table moved those
switches a second time.

VIDSYNC on F1.3.8dev1, ONE//e, PAL-accurate colour mode:

| Test | Switch | F1.3.8dev1 | Correction in this build |
|---|---|---|---|
| hg, gr | `$C050` TEXT | 1 cycle late | no delay |
| 80, dh | `$C00D` 80COL | 1 cycle early | no advance |
| mt | `$C00F` ALTCHARSET | 2 cycles early | 1 cycle of delay |
| mx, pg, hi, 8p, 8s, dy | `$C052`, `$C055`, `$C056`, `$C001`, `$C05E` | exact | no change |

Each renderer now has its own table in
`ps_sources/frontend/apple_cycle_renderer.c`:

| Switch | Clean renderer | PAL-accurate renderer |
|---|---|---|
| `$C050` TEXT | delay 1 | native |
| `$C052` MIXED | delay 1 | delay 1 |
| `$C00D` 80COL | advance 1 | native |
| `$C05E` DHIRES | native | native |
| `$C00F` ALTCHARSET | advance 1 | delay 1 |

The clean renderer does not change. The renderer selects the table from the
colour mode, which changes only at a frame start.

Limits:

- The PAL-accurate values come from one VIDSYNC run in ONE//e. Nobody has
  measured them on a physical //e without ONE//e.
- The October measurement did not record the colour mode. The conclusion
  that it used the clean renderer comes from the numbers: the new errors are
  the October corrections with the opposite sign.

## Build and validation

Only the ARM code changes. This package uses the FPGA build
`20261120T190553Z-fea5c6e9-full` of F1.3.8dev1 again. Packaging does not
rebuild the FPGA.

- Setup WNS **+0.160 ns**, hold **+0.047 ns**, pulse width **+0.265 ns**.
- No failing endpoints. Route, bus skew, and checked constraint bounds
  pass, with zero missing constraint objects.
- The run used a +0.000 ns export gate. The package check requires
  +0.020 ns.
- The four runs with the direction-source twin hook are all finished: two
  passed (+0.160 ns, this one, and +0.043 ns) and two failed (-0.045 ns and
  -0.166 ns). `TIMING_ATTEMPTS.json` lists all runs. Their reports are in
  `build/f138dev1-timing-attempts/`.

Checks:

- `test_renderer_phase.py` checks both tables and that the renderer selects
  the table from the colour mode.
- The host render harness runs the real renderer source. Scenario T5 has
  two new cases for the PAL-accurate table, with and without the vTW
  normalization. All harness scenarios pass.
- The other 11 test scripts that read the renderer source pass.
- The harness replaces the PAL-accurate signal model with a stub. So no
  host test shows the final pixels of that renderer. The check of the
  result is VIDSYNC on the card.
- The speech checks of F1.3.8dev1 did not run again. No speech file
  changed.

The package contains a new XSA-derived platform, FSBL, and both ARM
cores. Golden Boot stays at **B2.0.6**. This package has no Golden update.

## Hardware test

Nobody has flashed or tested this image on a card. Install `FIRMWARE.BIN`
through the normal firmware updater.

- VIDSYNC in ONE//e with a PAL-accurate colour mode: the hg, gr, mt, 80 and
  dh tests must be exact, and the other tests must stay exact.
- VIDSYNC in ONE//e with a clean colour mode (for example RGB): all tests
  must be exact, as in F1.3.2.
- The speech and bus tests of F1.3.8dev1 still apply.
