Text Overlay Card Interface

  • Version: 1.0 draft
  • Date: 2026-08-10
  • Signature: $54 ’T’
  • Reference implementation: Appletini One

1Overview

This document specifies a text overlay interface for Apple II video cards. A card that implements it shows a grid of character cells on top of its video output. An Apple II program controls the grid through the 16 I/O bytes of one slot. The interface is character-based like COUT, addressable like a Slinky RAM card, and fully readable: a program can ask what character and colors sit at any position.

  • Each cell holds a character byte (an index into a 256-glyph font) and an attribute byte (4-bit foreground color, 4-bit background color).
  • The program uploads its own font. Cell sizes from 5×7 to 32×64 pixels are supported.
  • Colors for new text come from $C022, the Apple IIgs text-color register, which the card observes on the bus.
  • The overlay draws above the normal video picture. Cells can be opaque, glyph-only, or fully transparent.

This specification describes only bus-visible behavior. How a card stores the grid, renders the glyphs, or scales its output is the implementer’s business.

Conventions

The card occupies one slot s (1–7). Its registers live in that slot’s DEVSEL space, $C080 + $10×s. This document writes register addresses as offsets, +$0 through +$F. In the 6502 examples, the X register holds s×$10, so $C080,X reaches offset +$0. Multi-byte values are little-endian. “Undefined” means: software must not depend on the value, and implementations may return anything.

Cursor rules

  • A CHAR write advances: XPOS + 1; if XPOS ≥ columns, XPOS = 0 and YPOS + 1; if YPOS ≥ rows, YPOS = 0.
  • Reads never advance. To read one cell, set XPOS and YPOS, read CHAR, read ATTR — the two reads see the same cell.
  • There is no auto-scroll. A terminal program issues CMD $04 itself when text reaches the bottom.
  • XPOS and YPOS may address cells outside the visible grid (up to 255 and 127). Those cells store data normally; they are simply not shown.

Commands and busy

  • CLEAR ($02) fills the whole character plane with $20 and the whole attribute plane with $00 — all 256×128 cells, visible or not. The result is an invisible screen (see §5).
  • SCROLL ($04) moves full storage rows: rows 1…rows−1 move up one row, all 256 columns; the last visible row clears to $20/$00. The cursor does not move.
  • CLEAR and SCROLL set STATUS bit 7 while they run. While busy, accesses to DATA, CHAR, ATTR, and CMD are undefined. Poll STATUS until bit 7 is 0.
  • ENABLE/DISABLE show and hide the overlay. A disabled overlay keeps all state, and every register stays live.

Reset state

After power-on or reset: overlay disabled, FONT_W = 8, FONT_H = 16, XPOS = YPOS = 0, window address = 0, planes cleared to $20/$00, $C022 latch = $F0 (white on black). The atlas content is undefined until uploaded.

3The memory window

ADDR_LO/HI/BANK and DATA expose one 18-bit address space, in the style of a Slinky RAM card. Use it for bulk work: font upload, raw attribute writes, saving and restoring screen regions.

RangeContentsAccess
$00000–$07FFFCharacter plane. Cell (x,y) at y×256 + x. Rows 0–127.read/write
$08000–$0FFFFAttribute plane, same layout: cell address + $08000read/write
$10000–$1FFFFFont atlas, 256 glyphs (see §6)write-only; reads undefined
$20000–$3FFEFReserved for future versions; do not access—
$3FFF0–$3FFFFID block: magic, version, capabilities (see §7)read-only; writes ignored

The row stride is fixed at 256 regardless of font size, so a cell’s address never changes — not when the font changes, and not when the machine switches video modes. Writes through the window are raw: they never touch the $C022 latch and never move the cursor.

4Canvas and grid

The overlay canvas covers the card’s active picture. Its pixel dimensions are implementation-defined and may change with the host’s video mode; the reference implementation uses 1280×800 when Super Hi-Res is active (STATUS bit 1 = 1) and 1120×768 for legacy modes (bit 1 = 0). Software must not assume these numbers: COLS and ROWS are the truth. They always report the visible grid of the current canvas with the current font, each minus one.

When the canvas changes, cells keep their stored addresses; only the visible window changes. Reference grids:

Writing FONT_W or FONT_H takes effect at once: COLS, ROWS, glyph addressing, and the rendered picture all follow. Set the font before you upload the atlas, because the atlas layout depends on the glyph size.

5Color and transparency

An attribute byte is foreground×16 + background — the $C022 convention: high nibble text, low nibble background. The card observes writes to $C022 on the bus and latches the most recent value; a CHAR write stamps that value into the cell. On a IIgs the register is real and the machine’s own text colors follow it too; on a II, II+, or //e the write reaches no motherboard device and is harmless. Programs that cannot write $C022 can set any cell’s colors directly through ATTR or the attribute plane.

The renderer applies one rule per cell:

  • fg ≠ bg: the cell is opaque. Set glyph bits show the foreground color, clear bits the background color.
  • fg = bg: only the glyph is drawn, in that color. Clear bits show the video underneath.
  • A fully transparent cell is a glyph with no set bits (normally $20, space) with fg = bg. This is what CLEAR produces.

The 16 colors are fixed in version 1.0 (4-bit channels scaled ×17):

Index0123456789ABCDEF

RGB 000D03009D2D 07255522F6AF 850F60AAAF98 0D0FF04F9FFF

These are the standard IIgs 4-bit colors, so $C022 values mean the same thing on the overlay as on a IIgs screen.

6Font atlas

The atlas holds 256 glyphs at window $10000, packed in character-code order with no gaps:

  • 1 bit per pixel; a set bit is a foreground pixel.
  • Rows are packed MSB-first: bit 7 of the first row byte is the leftmost pixel. row_bytes = (FONT_W + 7) / 8, unused low bits clear.
  • One glyph is row_bytes × FONT_H bytes, rows top to bottom.
  • Glyph c starts at $10000 + c × row_bytes × FONT_H.

Character bytes are raw atlas indices. The interface imposes no encoding: upload ASCII where you want ASCII, and put inverse or graphic glyphs at any free codes. Codes above the last uploaded glyph draw whatever the atlas holds there — upload all glyphs you intend to use.

The largest font (32×64, 256 bytes per glyph) fills the region exactly. The atlas region is write-only; keep a copy in host memory if you need to read it back.

7Card detection

Detection uses only the DEVSEL registers and the memory window — no ROM claim. It runs in three phases, and each rejects a different class of impostor. A single signature byte is not enough, because the DEVSEL space of other cards is live hardware: a real Slinky RAM card tracks writes at offset +$0 by design, and the floating bus of an empty slot echoes screen memory. The probe is also minimal by construction: the only writes it ever makes are the window-address writes it needs anyway.

PhaseTestRejects
1Read SIG = $54; read VER = valid BCD ≥ $10Almost everything, with reads only
2Write the ID-block address ($F0, $FF, $03) to ADDR_LO/HI/BANK; each reads backThe floating bus, input-only and stuck ports
38 DATA reads match the magic at $3FFF0RAM cards that track addresses — including a real Slinky; also reports capabilities

Etiquette is part of the protocol: phase 1 comes before any write, so a slot that fails is never written to. On some cards — a Disk II controller above all — every DEVSEL access has side effects; two reads of offsets +$E/+$F on an idle controller are the least intrusive probe possible.

The magic read is not optional. A real Slinky card passes phases 1 and 2 by construction if its +$E/+$F happen to satisfy phase 1: its address registers hold state exactly like ours. Only the magic separates a register file backed by RAM from this card — 8 chosen bytes at a fixed 18-bit address do not occur by accident.

; Entry: X = slot * $10.  Exit: carry clear = card found.
DETECT   LDA   $C08E,X      ; 1. reads only: SIG must be $54
         CMP   #$54
         BNE   NOCARD
         LDA   $C08F,X      ;    VER must be BCD, $10 or higher
         CMP   #$10
         BCC   NOCARD
         LDA   #$F0         ; 2. point the window at the ID block;
         STA   $C080,X      ;    the read-backs prove the registers
         LDA   #$FF         ;    hold state -- a floating bus cannot
         STA   $C081,X
         LDA   #$03
         STA   $C082,X      ;    ADDR = $3FFF0
         LDA   $C080,X
         CMP   #$F0
         BNE   NOCARD
         LDA   $C081,X
         CMP   #$FF
         BNE   NOCARD
         LDA   $C082,X
         CMP   #$03         ;    ADDR_BANK bits 7:2 read as 0
         BNE   NOCARD
         LDY   #0           ; 3. the magic makes it certain
MAGIC    LDA   $C083,X      ;    DATA, auto-increment
         CMP   IDSTR,Y
         BNE   NOCARD
         INY
         CPY   #8
         BCC   MAGIC
         CLC
         RTS
NOCARD   SEC
         RTS
IDSTR    ASC   "TOVERLAY"

Sixteen bus accesses in all. On success the window already points at $3FFF8, so the natural next step is free: keep reading DATA for the version, feature bits, and font limits.

The ID block

The last 16 bytes of the address space are a read-only ID block:

AddressBytesContents
$3FFF08Magic “TOVERLAY” = $54 $4F $56 $45 $52 $4C $41 $59
$3FFF81Interface version, BCD; equals VER
$3FFF91Feature bits: bit 0 palette upload, bit 1 streaming read port; others 0
$3FFFA2FONT_W minimum, maximum
$3FFFC2FONT_H minimum, maximum
$3FFFE2Reserved, $00

Registers answer “is the card here”; the ID block answers “for certain, and here is what it can do”. The block is normative: every implementation provides it, it needs no expansion-ROM claim, and it reads the same way on every machine.

8Programming examples

Initialize, once, at program start

; X = slot * $10 throughout.  1. detect  2. font  3. atlas  4. clear  5. enable
         JSR   DETECT
         BCS   FAIL
         LDA   #8
         STA   $C08A,X      ; FONT_W = 8
         LDA   #16
         STA   $C08B,X      ; FONT_H = 16
         JSR   LOADFONT     ; see below
         LDA   #$02
         STA   $C088,X      ; CMD: clear
WAIT     LDA   $C089,X      ; STATUS
         BMI   WAIT         ; bit 7 = busy
         LDA   #$01
         STA   $C088,X      ; CMD: enable

Upload an 8×16 font (4096 bytes)

LOADFONT LDA   #$00
         STA   $C080,X      ; ADDR_LO = 0
         STA   $C081,X      ; ADDR_HI = 0
         LDA   #$01
         STA   $C082,X      ; ADDR_BANK = 1  -> window $10000, the atlas
         LDA   #<FONT
         STA   PTR
         LDA   #>FONT
         STA   PTR+1
         LDA   #16
         STA   PAGES        ; page counter in zero page; X stays the slot index
         LDY   #0
PAGE     LDA   (PTR),Y
         STA   $C083,X      ; DATA, address auto-increments
         INY
         BNE   PAGE
         INC   PTR+1
         DEC   PAGES
         BNE   PAGE
         RTS

Print a string at (10, 5)

         LDA   #$F0
         STA   $C022        ; white on black for all text that follows
         LDA   #10
         STA   $C084,X      ; XPOS
         LDA   #5
         STA   $C085,X      ; YPOS
         LDY   #0
PRINT    LDA   MSG,Y
         BEQ   DONE
         STA   $C086,X      ; CHAR: stores char + colors, advances cursor
         INY
         BNE   PRINT
DONE     RTS
MSG      ASC   "HELLO, WORLD"
         DFB   0

Read the cell at (x, y)

         STA   $C084,X      ; A = column
         TYA
         STA   $C085,X      ; Y = row
         LDA   $C086,X      ; the character  (no advance on reads)
         PHA
         LDA   $C087,X      ; its attribute

9Compliance

Normative: the register offsets and semantics (§2), the window layout and 256-byte stride (§3), the attribute format, transparency rules, and palette values (§5), the atlas format and font limits (§6), the $C022 observation, the detection protocol, SIG/VER values, and the ID block (§7), and the busy contract (§2).

Implementation-defined: the slot; the canvas dimensions and when they change (reported through COLS/ROWS and STATUS bit 1); the overlay’s placement over the picture; how long CLEAR and SCROLL take (bounded by the busy bit).

Reserved for future versions: window $20000–$3FFEF (palette upload), CMD values above $04, STATUS bits 2–6, feature bits 2–7. A card returns VER > $10 only if it implements every rule of that version.
